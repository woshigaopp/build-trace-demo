# AI-Assisted Development Report

## 1. 需求理解与范围决策

这次题目的要求不是复刻完整 Atoms，而是在 6-8 小时时间盒内证明一条真实、可运行、可继续迭代的 AI App Builder 主链路。我们将 P0 锁定为：游客进入工作台，输入需求，后端生成完整 HTML，前端运行预览，平台保存消息和版本，用户继续修改或恢复旧版本，刷新后数据仍然存在。

用户熟悉 Java，因此后端选择 Java 21 和 Spring Boot。这个选择牺牲了与职位描述中 Python/Go/Rust 的直接匹配，但降低了无法解释代码和部署不稳定的风险。前端使用 React、TypeScript 和 Vite，生产数据使用 PostgreSQL，模型通过 OpenAI-compatible API 接入。

明确不做的内容包括复杂多 Agent、WebContainer、多文件依赖安装、微服务、Redis、MQ、OAuth、支付和独立发布每个生成应用。这些能力都可能有价值，但不能提高本次核心链路的可信度。

## 2. AI 协作方式

本项目没有运行 AutoMQ 大需求的完整重型 workflow。题目时间盒很短，只采用了其中四个原则：先锁定范围和非目标；把实现拆成可独立验证的小步骤；每完成一步立即编译、测试或浏览器验收；根据真实代码、测试和纠偏事实整理记录。

人负责锁定产品目标和关键取舍，包括使用可答辩的 Java 后端、优先完成真实生成闭环、选择版本历史作为延展能力，以及不以固定动画冒充多 Agent。AI 负责代码实现、测试补充、联调、浏览器验收、部署配置和文档整理。最终判断依据始终是可运行结果，而不是 AI 对代码的自我描述。

## 3. 实现与真实纠偏

实现顺序是后端数据模型和项目 API、前端工作台、SSE 模型链路、HTML 提取与 iframe 预览、持久化和版本回滚，最后进行浏览器主流程验收。生成链路只有在模型流完整结束、HTML 提取成功并通过基本完整性检查后，才会创建版本并替换当前预览；失败不会保存半份 HTML。

开发中发生了以下真实纠偏：

1. 本地页面从 `127.0.0.1:5173` 打开时，前端默认请求 `localhost:8080`，浏览器把它们视为不同来源并触发 CORS 失败。修复方式是让前端默认跟随当前 hostname，并让本地后端同时允许 `localhost` 和 `127.0.0.1`。生产环境仍要求显式配置准确的 Vercel origin。
2. 第一版 SSE 客户端在流提前结束时可能被当作成功。修复后，只有收到 `completed` 事件才算成功；`generation-error` 或提前结束都会抛错，并重新读取服务端项目状态，避免前端乐观消息与持久化状态不一致。
3. iframe 最初只有 `allow-scripts`。生成的待办应用使用标准表单提交事件，浏览器沙箱直接阻止了提交，因此输入后无法新增任务。增加 `allow-forms` 后，添加、完成和删除均通过浏览器实测；仍然没有启用 `allow-same-origin`。
4. 生成成功提示条最初位于工作区顶部，会短暂盖住预览、代码和版本标签。浏览器验收时发现必须先关闭提示才能打开版本历史，因此将提示移到右下角，避免阻断核心操作。

这些纠偏说明验证对象不仅是 Java 方法和 React 组件，还包括 hostname、浏览器安全策略、SSE 完成语义和真实点击区域等跨层契约。

## 4. 验证结果

后端集成测试覆盖项目持久化、消息与版本递增、恢复旧版本时创建新版本以及游客数据隔离。HTML 提取测试覆盖 Markdown 围栏、解释文字和不完整 HTML。前端执行 TypeScript 生产构建、ESLint 和高危依赖审计。

浏览器验收实际完成了以下路径：刷新恢复已有项目和 v1；在生成应用中添加、完成和删除待办；提交第二轮需求得到 v2；恢复 v1 并得到新的 v3；再次刷新后消息、当前预览和 v1/v2/v3 均存在。

当前没有配置真实模型 Key，因此本地浏览器验收走的是界面明确标记的 fallback。真实模型的 SSE 接入代码已经实现，但必须在部署环境配置模型 Key 后，再执行一次线上完整验收，才能把“真实模型调用成功”和“公网 Demo 可访问”标记为完成。

## 5. 后续演进

上线前的必要动作是接入 Neon、Railway、Vercel 和真实模型 Key，按标准演示脚本完成线上 E2E，并把地址写入 README。若继续产品化，优先级依次是独立沙箱域名和 CSP、认证与限流、Flyway 数据库迁移、生成并发控制、模型 token/成本治理，以及从完整 HTML 重写演进到结构化补丁和自动修复。

这套 AI Coding 方法在本题中的价值不是限制模型如何写代码，而是让需求理解、关键决定、实际执行和验证结果能够被人复核。最终交付与人的预期之间仍可能存在差异，但这些差异不再只隐藏在一份看似完成的代码里。
